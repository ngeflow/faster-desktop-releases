Hangout Online: Web-Based Version with a Local Server

Why we test Hangout Online in the browser first, and how the result gives confidence in the desktop app.

1. Purpose of This Document

This document explains our plan for Hangout Online on desktop. It tells you:

  • what we built first, and why it was straightforward;
  • what problem we met when we tested it;
  • the new approach: a web-based version with a local server;
  • why this approach gives us confidence in the desktop app.

2. The Starting Point: faster-app and faster-desktop

faster-app

faster-app is the mobile application for ngeShare. It runs on Android and on iOS. It contains the Hangout Online feature: a Member can follow the weekly Episode with video and the rules track.

faster-desktop

faster-desktop is the desktop version of faster-app. It is a copy of the faster-app code, with a desktop shell. The shell is Tauri 2. Tauri puts the app in a normal desktop window and adds a small Rust layer.

In other words: the user interface code is the same, but the container is different.

What changed from phone to desktop

The first work was to move Hangout Online from a phone to a desktop. This was the straightforward part. The product logic stays the same. The implementation details change, because the device is different.

🖱️

Input

A phone uses touch. A desktop uses a mouse and a keyboard. The code must react to clicks, hovers, and keys.

🖥️

Screen and layout

A phone screen is small and tall. A desktop window is wide and can change size. The layout must adapt.

🧭

Navigation

A phone uses swipe gestures and system back. A desktop uses visible buttons and a stable menu.

🎬

Media

Video download, cache, and playback must work in the desktop environment. This is the core of Hangout Online.

🔔

Notifications and links

Phone push notifications and phone deep links do not work the same way. The desktop needs other routes.

📦

Build and release

A phone builds with Expo and the app stores. A desktop builds with Tauri and produces installers for each system.

So the team adapts these implementation details inside faster-desktop. The learning content and the flow of Hangout Online do not change.

3. The Problem: Hard to Test with an AI Assistant

A Tauri desktop app is hard to test with an AI assistant (a large language model, or LLM). The AI assistant is our main tool to check changes.

Why it is hard

  • The assistant works best with text: source code, logs, and web pages. A Tauri window is a native desktop window, so the assistant cannot read it easily.
  • The assistant cannot click buttons in a native window in a simple and reliable way.
  • A build needs the Rust toolchain and platform libraries. Each build takes time.
  • A bug on desktop is often in the shell, not in the product code. It is then difficult to separate the two.

Result: the assistant cannot verify Hangout Online on desktop with confidence. We spend time on manual checks, and we still have doubt.

4. The New Approach: Web-Based Version with a Local Server

We change the approach. We make Hangout Online work in a web-based version first. The web-based version runs in a browser. Then we copy it into faster-desktop.

4.1 The parts

Web app (browser)

The faster-app user interface, exported for the web. It shows the Hangout Online screen and plays the Episode video.

Local Go server

hangout-online-service. A small HTTP server written in Go. It listens only on this computer.

faster-desktop (Tauri)

A desktop window that loads the same web app. It is a copy of the web-based setup.

▲
One product code, three containers. The web app is the single source. The browser container is where we test. The Tauri container is what we ship.

4.2 What the local Go server does

The web app cannot do all media work alone in the browser. So a local server helps it. The server runs on the same computer as the user.

Job What it means
Listen on localhost The server listens only on 127.0.0.1:34721. It is not open to the internet. Only the app on this computer can use it.
Download trusted media The server downloads the video and the rules track from trusted sources. It stores the files in a local cache.
Protect the cache The cache files are obfuscated per user. The server decrypts a stream on request.
Serve the video stream The server sends the video with HTTP Range support. The user can seek forward and back in the Episode.
Report status The server reports download progress, cache health, and errors. A small local dashboard shows this at http://127.0.0.1:34721/.

4.3 How a Hangout Online session works

1The user opens the web app in the browser.
2The web app asks the local server to prepare the Episode. It sends the media URLs.
3The server downloads the media and stores it in the cache.
4The web app reads the status until the Episode is ready.
5The web app plays the video from the local server. Seek works because of Range support.

4.4 Copy into faster-desktop

When the web-based version is correct, we copy it into faster-desktop. The Tauri window loads the same web app. The same local Go server runs next to it. The desktop user gets the same Hangout Online behavior.

5. Why This Gives Us Confidence

The rule is simple: if the web-based Hangout Online works, then faster-desktop is correct too. We do not need to test it again in the desktop shell.

Why the rule is valid

  • The product code is the same. The web app is one code base. Both containers load it.
  • The media path is the same. Both containers use the same local Go server, on the same address.
  • The AI assistant can test the web version well. It can read the page, run requests, and check the server endpoints.
  • The Tauri shell changes only the window, menus, and installers. It does not change the Hangout Online logic.

What the assistant checks in the browser

✅

Server health

GET /health returns "ok": true.

✅

Prepare

POST /episodes/{id}/prepare starts the download.

✅

Status

GET /episodes/{id}/status becomes ready.

✅

Playback

The video plays. Seek works. The rules track plays.

✅

Errors

Bad input gives a clear error. The cache repair works.

✅

Interface

The Hangout Online screens show correct data and controls.

6. The Way of Working from Now On

  1. Develop Hangout Online in the web-based version. Use the browser and the local Go server.
  2. Test with the AI assistant. The assistant checks the pages and the server endpoints.
  3. Fix all problems in the web-based version. Keep the code one source.
  4. Copy into faster-desktop. Apply only the desktop-specific parts (window, menus, installers).
  5. Ship with confidence. No second test round for the desktop shell.

Only one case needs a manual desktop check: when we change the Tauri shell itself. For example, a change to the window, the menus, or the installer. For all Hangout Online work, the browser test is the source of truth.

7. Summary

Before

Phone app → desktop copy (Tauri). Straightforward to build, but hard to test with an AI assistant.

Now

Web-based app + local Go server. Easy to test. Then copy into faster-desktop.

Payoff

One test, one source of truth. A green web test means a correct desktop app.
